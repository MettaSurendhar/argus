A RAG + MCP agent that diagnoses Kubernetes incidents — retrieves runbook
context, checks live cluster state, and returns a root-cause hypothesis
with confidence and citations, not just an answer.

## What it does

- **Retrieves** relevant runbook context from a local Chroma vector store
- **Checks live cluster state** via a read-only Kubernetes MCP server —
  pod status, logs, events
- **Synthesizes** a root-cause hypothesis with an explicit confidence
  level and citations back to the runbook and live signal that informed it
- **Observes itself**: every step (retrieval, MCP calls, LLM call) is
  wrapped in an OTel span, exported to a self-hosted SigNoz instance —
  so you can see _where_ the agent's reasoning breaks down, not just
  whether it got the right answer

## Project structure

```
argus/
├── src/                # the agent itself (RAG + MCP + LLM)
├── instrumentation/    # OTel-instrumented version of the agent, exports to SigNoz
├── data/
│   ├── knowledge_base/     # runbooks used for retrieval
│   └── demo_scenarios/     # the 3 Kubernetes failure scenarios
├── docs/               # scenario docs, manual eval results, raw run logs
├── casting.yaml        # Foundry deployment config for SigNoz (source of truth)
├── Dockerfile
└── setup.sh            # orchestrates the full run, start to finish
```

`casting.yaml.lock` and `pours/` are generated by `foundryctl cast`, not
committed, regenerate locally when needed.

## Prerequisites

- Docker (native Engine — not Docker Desktop on Windows)
- [minikube](https://minikube.sigs.k8s.io/docs/start/) + `kubectl`
- [foundryctl](https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md)
- Python 3.11+ — only for running things by hand, not needed for `setup.sh`
- **Windows:** use WSL2, native filesystem (e.g. `~/projects/argus`), not
  `/mnt/c/` — see [`docs/setup.md`](docs/setup.md) for why

Full setup walkthrough: [`docs/setup.md`](docs/setup.md).
Errors? Check [`docs/faq.md`](docs/faq.md) first.

## Setup

Once the prerequisites above are in place:

```bash
cp .env.example .env   # fill in your GROQ_API_KEY (or OPENROUTER_API_KEY)
chmod +x setup.sh
./setup.sh
```

Starts (or reuses) minikube, deploys SigNoz via Foundry, builds the
agent's Docker image and RAG index, then runs all 3 demo scenarios in
sequence.

**Running things by hand** (single scenario, outside Docker, or an
intermediate step):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env

python -m src.ingest.build_index   # build the RAG index

kubectl apply -f data/demo_scenarios/scenario_1_oom.yaml
python -m instrumentation.main "why is this pod crashing" default my-oom-pod
```

## Alerts

- **Diagnose latency high** — fires when p95 latency on `diagnose`
  exceeds threshold over 5 minutes
  ![Latency alert rule](docs/screenshots/alert-latency-rule.png)
- **Silent failure (diagnose incomplete)** — fires when `diagnose` span
  count exceeds `llm_call` span count, meaning runs started but never
  reached the LLM step
  ![Silent failure alert rule](docs/screenshots/alert-silent-failure-rule.png)
