# Argus

Argus is a small RAG + MCP agent that diagnoses Kubernetes incidents. Given a question like "why is this pod crashing", it retrieves relevant runbook context from a local knowledge base, checks live cluster state through an MCP server, and produces a root-cause hypothesis with an explicit confidence level and citations back to which runbook and which live signal informed the answer.

## How SigNoz fits in

Every real step Argus takes, retrieval, the MCP tool calls, the LLM call, is wrapped in its own OpenTelemetry span and exported to a self-hosted SigNoz instance. The point isn't just to watch the agent run, it's to see _where_ its reasoning actually breaks down: a wrong retrieval, a slow tool call, a bad LLM response. SigNoz's dashboards and alerts turn that into something you can actually catch instead of noticing by accident in a terminal log.

## Why this exists

I wrote about this gap directly in [AI Agents Aren't Ready for IT Operations Yet](https://medium.com/@mettasurendhar/ai-agents-arent-ready-for-it-operations-yet-and-now-there-s-a-benchmark-that-proves-it-8e62a230e2d3): IBM Research's ITBench benchmark tests how well AI agents handle real IT-operations incidents, and even the best-performing agents in one independent run resolved only a small minority of SRE scenarios. Existing tools are good at producing an answer. None of them make it easy to see _why_ that answer is right or wrong, or which stage of the agent's own reasoning actually failed. Argus is a small, honest attempt at closing that second gap, using SigNoz to make the agent's own execution observable, not just its output.

## Architecture

```
 Question -------------------> Planner
                                   |
                 -------------------------------------
                 |                |                   |
                 v                v                   v
           Retriever      MCP Tool Client        (both feed into)
        (Chroma vector    (kubernetes-mcp-             |
         store, runbook    server, read-only)          |
         chunks)                |                      |
                 |                v                     |
                 |          Live pod state,              |
                 |          logs                          |
                 -------------------------------------
                                   |
                                   v
                             LLM synthesis
                        (hypothesis + confidence
                          + cited sources)
                                   |
                                   v
                               Answer

 ------------------------------------------------------------
 Every step above is wrapped in an OTel span and exported to
 SigNoz: retrieve_runbooks -> k8s_describe_pod -> k8s_get_logs
 -> llm_call, all nested under one root "diagnose" span.
 ------------------------------------------------------------
```

## Folder structure

```
argus/
├── src/                # the agent itself (RAG + MCP + LLM)
├── instrumentation/    # OTel-instrumented version of the agent, exports to SigNoz
├── data/
│   ├── knowledge_base/     # runbooks used for retrieval
│   └── demo_scenarios/     # the 3 Kubernetes failure scenarios
├── docs/               # scenario docs, manual eval results, raw run logs
├── casting.yaml        # Foundry deployment config for SigNoz (source of truth)
├── Dockerfile
└── setup.sh            # orchestrates the full run, start to finish
```

`casting.yaml.lock` and `pours/` are generated by `foundryctl cast` when you deploy SigNoz — not committed, regenerate them locally whenever you need them.

## Prerequisites

- Docker (native Docker Engine — **not** Docker Desktop on Windows, see below)
- [minikube](https://minikube.sigs.k8s.io/docs/start/) + `kubectl`
- [foundryctl](https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md) (deploys SigNoz)
- **Windows only:** run all of the above inside WSL2, not PowerShell — Docker Desktop's virtualization layer has a known SigNoz/ClickHouse Keeper crash bug on Windows. Also keep the project on WSL2's **native filesystem** (e.g. `~/projects/argus`), not `/mnt/c/` or `/mnt/d/` — file I/O across that boundary is slow enough to crash the whole WSL2 VM mid-`docker build`. `setup.sh` checks for this and warns if it's detected.
- Python 3.11+ — only needed for the "running things by hand" route below, not for `setup.sh` itself.

Full step-by-step instructions, including WSL2 setup and what to do if
Docker is already installed some other way, are in
[`docs/setup.md`](docs/setup.md). Hit an error? Check
[`docs/faq.md`](docs/faq.md) first.

## Setup

Once the prerequisites above are in place:

```bash
cp .env.example .env   # fill in your GROQ_API_KEY (or OPENROUTER_API_KEY)
chmod +x setup.sh
./setup.sh
```

This starts (or reuses) a minikube cluster, deploys SigNoz via Foundry,
builds the agent's Docker image, builds the RAG index, then injects each of
the 3 demo scenarios and runs the agent against them in sequence, printing
what it's doing at every step.

### Running things by hand

Useful if you want to re-run a single scenario, work outside Docker, or poke
at an intermediate step instead of the full `setup.sh` sequence:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # fill in your LLM provider's API key

python -m src.ingest.build_index   # build the RAG index

# run a scenario, see docs/scenarios.md for all 3
kubectl apply -f data/demo_scenarios/scenario_1_oom.yaml
python -m instrumentation.main "why is this pod crashing" default my-oom-pod
```

## Alerts

**Argus diagnose latency high** — fires when p95 latency on the `diagnose` span goes above threshold in a 5-minute window, catches the agent getting suspiciously slow.

![Latency alert rule](docs/screenshots/alert-latency-rule.png)

**Argus silent failure (diagnose incomplete)** — fires when the count of `diagnose` spans exceeds the count of `llm_call` spans in the same window, meaning some runs started but never reached the LLM step. This one was built directly in response to the dashboard surfacing exactly this pattern in earlier dev-time runs.

![Silent failure alert rule](docs/screenshots/alert-silent-failure-rule.png)
