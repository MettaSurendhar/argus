## Observations / dead ends

- groq (openai/gpt-oss-120b) across all 3 scenarios: retrieval, live-signal grounding, and final hypotheses were all correct and high-confidence on the first pass — no retrieval misses or wrong runbook matches observed.
- openrouter (meta-llama/llama-3.3-70b-instruct) also went 3/3 correct with correct runbook retrieval and high confidence across all scenarios. Compared to groq, its `live_signals_used` field was less specific/generic ("Live pod state", "Recent logs" every time) rather than naming the actual concrete signal values groq extracted — worth flagging as a potential provider/model-level difference in how well the model follows the structured-output instructions for that field, even though the underlying hypothesis text itself did reference the specific details.
- openrouter's hypotheses tended to hedge more ("likely does not exist," "either not running, not listening... or not properly configured") vs groq's more committed single-cause phrasing — both graded as correct here, but this could be a useful axis (hedging/specificity) to track in the ablation study, not just correct/incorrect.
- groq (openai/gpt-oss-20b) also went 3/3 correct with correct runbook retrieval and high confidence across all scenarios, matching the 120b groq run's style of concise, specific `live_signals_used` entries (vs openrouter's more generic "Live pod state"/"Recent logs" labels). Notably it surfaced an extra specific detail in scenario 3 (possible service selector mismatch) that neither of the other two runs called out explicitly.
- Across all three run sets so far (groq/120b, openrouter/llama-3.3-70b, groq/20b), every single run was correct with high confidence on the first pass — no wrong-runbook retrievals or missed live signals observed yet across 9 total runs. If this pattern holds, these demo scenarios may be too easy to differentiate model/provider quality on accuracy alone; the more informative signal so far is in the qualitative differences (specificity of `live_signals_used`, hedging language, extra corroborating details) rather than correct/incorrect — worth designing harder/more ambiguous scenarios for the ablation study to actually surface accuracy gaps.
- Each `src.main` invocation currently spawns a fresh MCP server per tool call (`pods_get`, `pods_log`) rather than reusing one session — not an accuracy issue, but worth noting as a latency/perf observation for the paper if it comes up later.
